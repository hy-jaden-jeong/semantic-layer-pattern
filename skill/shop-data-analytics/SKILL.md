# shop-bi 지표 분석

지표의 뜻은 이 skill에 없다. 정의 저장소(dbt project)의 정의 폴더(`semantic/`)에 있고, 이 skill은 그 폴더를 최신 main으로 찾아 그곳 `README.md`의 "질문에 답하기"를 따르게 한다.

## 1. 정의 폴더를 찾는다

이 skill 폴더의 `scripts/locate.sh`를 인자 없이 실행한다.

- stdout 한 줄이 정의 폴더의 절대 경로다. stderr의 `key=value` 줄을 읽는다.
- `skill_updated=1`이면 이 skill이 방금 갱신됐다. 이 SKILL.md를 다시 읽고 처음부터 따른다.
- `skill_freshness=unmanaged`면 이 skill이 skill 저장소 clone이 아니라(복사 설치 등) 자동 갱신하지 않았다. 그대로 진행하되 사용자에게 symlink 설치를 권한다.
- 작업 디렉터리가 정의 저장소 checkout이어도 늘 origin/main의 정의를 쓴다(`source=main ref=main@<sha>`). checkout 밖에서 main이 받은 사본과 같으면 다시 받지 않는다(`via=cache-current`).
- `freshness=unknown`이면 최신인지 확인하지 못한 정의다(로컬의 가장 최근 정의: checkout의 origin/main 또는 받아 둔 사본). 답의 주의 줄에 "최신 확인 못 한 정의(마지막 확인 <last_checked>)"를 적는다. 기준 block을 쓸 때는 ref에 적는다.
- 종료 코드가 0이 아니면 멈추고 stderr의 `error=` 줄을 사용자에게 그대로 전한다. 기억이나 mart model의 SQL을 직접 읽어 지어낸 정의로 답하지 않는다.
  - 2: git이 없다
  - 3: main에 semantic layer가 없다
  - 4: 정의를 받지 못했고(네트워크·권한) 가진 정의도 없다
  - 5: skill이 정의 형식보다 낡았거나(갱신을 시도한 뒤에도 낮다) index.md 형식 오류다
  - 6: skill 저장소를 자동 갱신할 수 없다(안내된 명령을 사용자가 실행)
- 한 대화에서는 처음 찾은 정의 폴더와 ref를 끝까지 쓴다(turn마다 정의가 다르면 앞 답과 견줄 수 없다). 날이 바뀌었거나 사용자가 정의를 고쳤다고 하면 다시 실행하고, ref가 달라졌으면 답에 적는다.

## 2. 지표를 고르고 SQL을 쓴다

그 폴더의 `README.md`를 열고 "질문에 답하기"를 차례대로 따른다. 용어 고르기, 합산 규칙, 공통 규칙, join, status, 기준 block이 모두 거기 있다. 이 skill에 다시 적지 않는다.

## 3. 실행

- 값을 묻거나("몇 명", "추이 보여줘") 분석을 맡기면 실행 요청으로 본다. 정의나 SQL만 달라고 하면(답을 파일로 쓰라는 지시 포함) 돌리지 않고 SQL만 준다.
- SELECT만 돌린다. 쓰기·DDL·권한 변경은 하지 않는다. 집계한 결과만 가져오고 원본 row를 통째로 가져오지 않는다.
- 실행 방법은 대화에서 한 번 정하고 끝까지 쓴다. 사용자가 말한 도구, 없으면 세션에 이미 있는 warehouse 도구(CLI, MCP, SQL 도구) 차례로 찾는다. profile이나 warehouse가 여럿이면 어느 것을 쓸지 묻고, 하나면 쓰기 전에 그 이름을 한 줄로 알린다.
- 특정 개인 경로·profile을 전제하지 않고, token 값을 읽거나 출력하지 않는다. 방법을 찾지 못하면 SQL만 주고 연결 방법을 묻는다.
- 정의 저장소 checkout 안에서 돌고 있고 그 root에 `make build`(dbt build)가 만든 DuckDB 파일(`shop_bi.duckdb`)이 있으면, 다른 도구가 없을 때 그 파일을 읽기 전용으로 연다(`duckdb -readonly shop_bi.duckdb` 또는 Python `duckdb.connect(path, read_only=True)`).

## 4. EDA를 대화로 이어 간다

한 turn에 질문 하나를 답하고, 다음에 볼 것은 사용자가 고른다. 고르지 않은 분석을 앞질러 돌리지 않는다.

- 시작: 주제 없이 분석을 맡기면("자유롭게 분석해 보자") 묻지 않고 개요부터 본다. `index.md`에서 grain이 날짜뿐인 table의 `confirmed` metric 두세 개를 골라 집계 query 1~2개로 범위와 최근 추이를 보이고, 눈에 띄는 신호를 2~3개 짚는다. 무엇을 왜 골랐는지 한 줄로 적는다. 선택지는 그 신호에서 뽑고, 마지막 하나는 [다른 주제]로 두어 나머지 table을 사람이 알아볼 주제 이름 서너 개로 묶어 적는다(예: 판매자 헬스스코어, 판매자 월 사용량, 결제 퍼널). table 이름은 쓰지 않는다. 무엇을 볼 수 있는지 물었거나 실행 방법이 아직 없으면 query 없이 주제 선택지만 보인다.
- 한 turn에 보는 것. 필요한 것만 고른다.
  1. 범위(주제의 첫 turn에는 꼭): 기간, row 수, 빈 값, table의 마지막 날짜(스냅샷이면 as_of_date), 데이터가 시작된 날. 온전하지 않은 기간(시작한 달, 진행 중인 달, 한꺼번에 들어온 날)은 비교에서 빼고 뺐다고 적는다
  2. 추이: 일·주·월 단위 값과 변화율. 합산 규칙(`rollup`)이 허락하는 grain으로만 묶는다
  3. 분포: 구간별 개수, 중앙값·분위수, 상위 몇 개의 비중
  4. 비교: 그룹·기간끼리 같은 정의로 견준다. 정의나 variant가 다르면 견주지 않고 그 사실을 적는다. 진행 중인 기간은 같은 길이끼리, 평일·주말 구성이 다르면 그것도 맞춰 견준다
  5. 쪼개기: 전체 변화를 그룹으로 나눌 때는 변화율이 아니라 전체 변화에 대한 기여도로 줄 세우고, 그룹 크기(mix)가 바뀌었는지 비율(rate)이 바뀌었는지 가른다. "어디서"까지는 `확인`, "왜"는 `추정`이다
  6. 이상치: 튀는 날·그룹을 짚는다. 실제 변화라고 쓰기 전에 차례로 본다. ① 데이터가 온전한가(빈 날, 시작한 날, 한꺼번에 들어온 날) ② 그 metric 파일의 `description`·`caveats`와 table 정의에 기준이 바뀐 날짜, 측정이 안 되는 기간, 창 길이가 적혀 있는가. 30일 창이나 MAU 같은 rolling 값은 기준이 바뀐 날부터 창 길이만큼 옛 기준과 섞인다 ③ `not_applied` 규칙(내부 판매자 섞임)
- 발견마다 표지를 붙인다: `확인`(query 결과로 봤다), `정의`(정의 파일에 적혀 있다), `추정`(둘 다 아니다). 추정에는 무엇을 보면 확정되는지 한 줄을 적고, 그 확인을 다음 분석 선택지에 넣는다. 결론이 고른 기간·뺀 날·기준에 따라 뒤집히면 그 사실도 한 줄 적는다.
- 이어 가는 조건: 기간, variant, 내가 건 규칙, 비교에서 뺀 날은 다음 turn에도 그대로 쓴다. 답의 `조건:` 줄에 적고, 바꿨으면 무엇을 왜 바꿨는지 적는다. 사용자가 번호로 답하면 그 선택지에 적은 질문 그대로 답한다.

## 5. 차트와 장표

- 장표는 사용자가 차트·장표를 말했거나, 값이 12개를 넘는 추이처럼 표로 읽히지 않을 때 만든다. 탐색하는 turn에는 1장까지, 여러 장은 [정리]를 골랐을 때 만든다.
- 차트나 장표로 설명할 때는 `diagram-slides` skill(https://github.com/hy-jaden-jeong/work-skills, line·bar 차트 견본 포함)을 Skill 도구로 불러 그 규칙대로 장표 1~3장을 만든다. 장표에는 실행한 SQL 결과의 값만 쓴다.
- `diagram-slides`가 설치돼 있지 않으면 표와 글로 답하고, 사용자에게 그 skill 설치를 권한다.

## 6. 답 모양

결론 한 줄(숫자 포함) → `조건:` 한 줄 → 장표(만들었으면) → 표 하나 → 발견 3개까지(표지 포함) → 돌린 SQL → 주의 한두 줄. 값을 낸 답이면 그 뒤에 다음 분석 선택지를 따로 붙인다.

- 표는 10 row 안팎으로 줄인다(상위·요약). 전체는 요청하면 준다.
- SQL은 결론을 낸 것만 싣는다. 범위 확인 같은 보조 query는 무엇을 봤는지 한 줄로 적고, 요청하면 보인다.
- 사용자는 데이터를 보는 사람이다. 답 글에 semantic layer 안의 이름(metric 이름, variant, status 값, question id, YAML, 정의 파일 경로)을 쓰지 않고 지표의 뜻으로 쓴다(예: `hs_order_count_30d` → "최근 30일 주문 수"). 무엇을 돌려 확인했는지는 SQL로 보인다. SQL 안의 table·column·code 값은 그대로 둔다.
- README의 기준 block은 대화 답에 보이지 않는다. 그 안에서 사용자가 알아야 할 것만 주의 줄에 사람 말로 적는다. 답을 파일로 쓰라는 지시가 있거나 사용자가 기준·근거를 물으면 block을 README 형식 그대로 쓴다.

```
다음 분석 (번호나 말로 답한다)
1. (추천) [검증] <볼 것: 지표의 뜻, 나누는 기준, 기간> — <방금 결과의 어느 숫자 때문인가>
2. [쪼개기] …
3. [견주기] …
4. [정리] 여기까지를 요약과 장표로 묶는다
```

- 2~4개를 쓴다. 방금 결과에서 나온 것만 쓰고, 종류(검증, 쪼개기, 넓히기, 견주기, 정리)가 겹치지 않게 고른다. 추천 하나를 맨 위에 두고 `(추천)`을 붙인다. 여러 개를 고르면 차례로 답한다. 같은 주제로 세 turn을 넘기면 [정리]를 꼭 넣는다.
- 선택지 하나에 질문 하나, 바로 답할 수 있는 것만 쓴다: metric이 `index.md`에 있고, 나누는 기준이 그 table의 dimension이고, rollup과 join 경로가 허락한다. 정의에 없는 길은 선택지에 넣지 않고 "mart에 없다" 한 줄로 알린다.
- 번호만 보고도 뜻이 통하게 쓴다. 판매자 이름·회원 이름이 필요한 선택지는 id나 집계로 바꿔 쓴다.
- 선택 화면 도구를 쓰지 않고 글로 쓴다. 답을 다 쓴 뒤에 붙이고, 선택을 기다리느라 답을 미루지 않는다.
- 붙이지 않는 때: 답을 파일로 쓰라는 지시, 질문 여러 개를 한 번에 받은 일괄 작업, 정의·SQL만 준 답(이때는 "돌려 볼까" 한 줄), 사용자가 그만 붙이라고 한 대화.
- [정리]를 고르면 발견 목록(표지 포함), 쓴 지표와 주의할 점(확정되지 않은 정의, 확인 중인 질문)을 사람 말로, 장표 1~3장, 다시 돌릴 SQL 묶음을 낸다.

## 7. 어디서나 지킨다

- 정의에 없는 지표는 없다고 답하고 가까운 지표를 알려 준다. SQL을 짓지 않고, 정의 밖의 뜻을 추측하지 않는다.
- 판매자 이름·회원 이름·이메일 같은 PII를 SQL 예시, 표, 장표, 답에 쓰지 않는다. 결과에 PII가 나오면 id나 집계로 바꿔 보인다.
- 정의가 없거나 모호하고 README로도 풀리지 않으면 멈추고 무엇이 없는지 알린다. 정의를 고쳐야 하면 정의 저장소 checkout에서 그곳 `README.md`의 "정의 쓰기"대로 고치라고 알린다.
